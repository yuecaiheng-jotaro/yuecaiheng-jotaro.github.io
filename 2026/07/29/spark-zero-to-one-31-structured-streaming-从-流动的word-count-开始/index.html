学习目标

  • 这一讲要把 Structured Streaming：从“流动的Word Count”开始 放到一条 Spark 作业里理解：数据从哪里读入，经过哪些转换，何时触发计算，哪里会产生 Shuffle，最终由哪些 Executor/Task 完成。
  • 读完后不应只会写 API，而要能说清它在执行计划、Stage 划分、分区变化、内存/磁盘/网络压力中的具体表现。
  • 复习时建议保留三个证据：最小代码、explain 输出、Spark UI 关键指标；没有证据的调优很容易变成玄学。

  • 观察入口：Spark UI、执行计划、Stage/Task 指标、Shuffle 读写、Executor 内存和外部系统吞吐。

  • 行动顺序：先用最小样例复现，再逐步放大数据量观察计划、指标和瓶颈变化。
  • 主要风险：只看 API 是否跑通，不看执行计划、数据分布、资源压力和长尾 Task。

实战清单

  • 定位性能问题时，先从 Spark UI 的 Job/Stage/Task 层观察耗时、Shuffle、数据倾斜和长尾任务。
  • 涉及 Shuffle 的算子要重点检查分区数、Key 分布、序列化、磁盘落地和网络传输。
  • 写 DataFrame/Spark SQL 时，配合 explain 看逻辑计划和物理计划，确认优化器是否按预期工作。
  • 流处理任务要把输入速率、触发间隔、状态大小、Watermark 和 checkpoint 放在一起看。
  • 机器学习任务要把特征处理、训练、评估和预测封装成可复用 Pipeline，避免训练和线上口径漂移。

易错点

  • 只记 API 名称，不看 explain 和 Spark UI，导致性能问题出现时无法定位。
  • 把本地小样例的结论直接套到大数据量，忽略分区、倾斜、Shuffle 和资源配置。
  • 调参数没有实验记录，无法判断优化是偶然波动还是机制真的被改善。
