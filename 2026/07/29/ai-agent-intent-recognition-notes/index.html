这篇是极客时间《AI Agent 系统设计面试现场》中“第一章：意图识别”4 讲的学习笔记。它不是逐字稿，而是按照我自己的理解，把课程里的工程问题、方案套路、面试表达和可落地清单重新组织了一遍。

原课程地址：AI Agent 系统设计面试现场

总览：意图识别到底在 Agent 里解决什么

意图识别不是给用户输入贴一个分类标签，而是在决定 Agent 后续应该怎么工作：加载哪套 Prompt 或 Spec、组织哪些上下文、调用哪些工具、进入哪个业务流程，以及是否需要拒识或澄清。

如果把 Agent 看成一个“会做事的系统”，意图识别就是需求分析入口。用户说话天然是松散的，可能省略主语、临时改口、使用指代词、使用业务黑话，也可能一句话里包含多个目标。一个成熟 Agent 不能指望用户按接口文档说话，而要先把自然语言里的目标、参数和约束整理出来。

我把这 4 讲串成一条主线：

  1. 第 1 讲先处理“用户到底说了什么”，也就是输入规范化。
  2. 第 2 讲回答“用户想干什么”，建立意图识别、Slot Filling、拒识、澄清和评估。
  3. 第 3 讲解决“为什么识别不准”，给出层次意图、检索、动态 few-shot、正交化、多意图、向量兜底等高级策略。
  4. 第 4 讲把这些能力包装成面试竞争力：简历怎么写、项目怎么讲、v0/v1/v2 怎么组织。

01：用户输入规范化

第一讲的核心观点是：在识别意图前，系统往往得先理解用户输入。用户输入规范化也可以叫输入归一化、输入理解，本质是把“随口说的话”转成后续模块能稳定消费的表达。

常见输入问题

课程里把用户输入问题分成几类，我理解成 6 个桶：

  • 指代问题：用户用“这个”“那个”“第二个”“刚才那个”等词代替具体对象。
  • 缺失问题：句子里缺主语、宾语、动作对象或关键约束。
  • 表达问题：口语化、病句、倒装、跳跃、临时改口。
  • 词义问题：同义词、缩写、内部代号、行业黑话、多义词。
  • 主观判断问题：例如“最划算”“高级一点”“适合生产”，标准不天然明确。
  • 外部事实问题：例如“最近更火”“现在最便宜”，需要实时数据或工具结果才能确定。

这里最值得警惕的是：有些问题看起来像模型推理不强，其实是系统没有把上下文召回、关键事实管理、指代消解这些基本活儿做好。比如用户上一轮聊某家公司，下一轮问“市场占有率如何”，系统如果只回答整个市场，而不结合上一轮公司主体，就说明输入规范化和上下文管理都出了问题。

规范化的时机

输入规范化不是只能放在一个固定位置。课程给出的三个时机很实用：

  • 意图识别之前：适合通用 Agent、C 端 Agent。先把用户输入整理干净，再进入意图识别，工程边界最清楚。
  • 和意图识别一起：适合用户输入比较规范、场景比较收敛的专属 Agent。
  • 执行过程中处理：适合依赖工具结果或深层上下文的问题，比如“最有性价比”这类评价，往往只有检索商品、价格、质量等信息后才能量化。

我的理解是，实际系统里常常是“两段式”：前置阶段先处理明显的指代、省略、黑话和病句；执行阶段再处理依赖检索、计算、实时数据和业务规则的深层规范化。

Prompt 职责边界

输入规范化的 Prompt 最容易犯的错，是让模型“顺手把后面的事也做了”。所以它必须有清晰职责边界。

它应该做：

  • 指代消解。
  • 省略句补全。
  • 病句修正。
  • 术语标准化。
  • 黑话解释。
  • 多义词消歧。
  • 判断是否需要澄清。
  • 判断是否需要搜索或工具补充事实。

它不应该做：

  • 直接回答用户问题。
  • 直接执行工具。
  • 做最终推荐或完整方案。
  • 擅自判断业务意图。
  • 强行补充低置信事实。
  • 伪造实时信息。

进阶方案

第一讲最有价值的部分，是把输入规范化和上下文深度绑定起来。

第一个方案是结合用户画像和关键事实。用户长期讨论某个语境时，同一个词应该优先按这个语境解释。比如同一个缩写在 IT、医疗、金融里含义不同，系统不能脱离行业和用户历史强行解释。

第二个方案是“属性 + 检索”。当用户说“你上次推荐的看樱花那个地方”时，系统不只是找“那个”，还要根据“看樱花”“旅游”“上次推荐”这些属性去历史对话里召回候选，再让模型推断目标对象。

第三个方案是行业画像和词汇表。把黑话、缩写、项目代号沉淀到词汇表里，并区分公共词汇表和用户个人词汇表。词汇表可以来自人工整理，也可以来自离线分析：当某个词被多人、多次、连续讨论时，标记为候选词，再进入审核或自动沉淀。

第四个方案是量化主观词。比如“性价比”不能粗暴等同于“便宜”。在电商里，它可能是同价位质量更好，也可能是同质量价格更低，还可能和品牌、售后、配置、活动相关。凡是不能量化的形容词，都会让 Agent 输出漂移。

02：三层意图识别机制

第二讲回答的是基础工程问题：什么是意图识别，为什么要独立做，Prompt 怎么写，识别不出来怎么办，如何结合 Slot Filling，以及怎么评估效果。

意图识别不是一个 intent 字段

最简化的意图识别，是从候选枚举里选出一个 intent。但真实系统通常需要两部分输出：

  • intent classification：用户要进入哪个业务流程。
  • Slot Filling：这个流程需要哪些关键参数。

例如“帮我推荐一台适合写代码的轻薄本”，不只是识别为商品推荐，还要抽取类目、用途、偏好、预算缺失等信息。否则后续流程仍然不知道怎么行动。

为什么要独立做意图识别

一个常见追问是：既然后面有 ReAct 或 TAO，为什么不让 Agent 在循环里自己判断？

课程给出的工程理由很扎实：

  • 意图影响 Prompt / Spec 加载。售前推荐和售后退款的业务规范完全不同。
  • 意图影响上下文组织。售前需要用户画像、商品候选、偏好；售后需要订单、物流、退款政策。
  • 意图影响工具选择。商品检索、订单查询、退款申请、文档生成本来就是不同工具链。

所以独立意图识别的价值不是“多一个分类步骤”，而是让后面的 Agent 主流程更可控、更可调试、更可评估。

意图识别 Prompt 怎么写

一个可用 Prompt 至少包含 4 类信息：

  • 候选意图：系统支持哪些意图，不允许模型自造 intent。
  • 意图边界：容易混淆的意图必须写清区别。
  • 槽位定义：每个意图要抽哪些参数，哪些必填，哪些可选。
  • few-shot：覆盖最容易混淆的例子，必要时加入正反例。

还要给模型两个出口：

  • unsupported：用户意图超出系统能力，拒识。
  • unclear：用户信息不足或边界不清，澄清。

这两个出口非常重要。很多系统为了“显得聪明”，会把任何输入强行归到某个意图上，结果后续越做越错。成熟系统应该允许自己说“不支持”或“我需要再确认一下”。

三层机制

课程推荐的三层意图识别机制是：

  • 第一层：代码层。包括按钮、页面状态、关键字、正则、规则引擎、上下文状态判断。特点是快、准、便宜、稳定。
  • 第二层：轻量模型。适合明确但不好写死规则的输入，比如普通商品推荐、订单查询、文档生成。
  • 第三层：深度推理模型。处理复杂表达、强上下文依赖、多轮切换、多意图、隐含信息补全。

关键是第二层如何判断“没识别出来”。不能只让模型输出 intent，还要输出置信度，并结合规则命中、向量相似度、历史表现等信号。置信度高可以直接接受，中间区间可以仲裁或澄清，低置信度则进入深度模型。

Slot Filling 与约束

Slot Filling 不只是抽参数，还要识别缺失项、硬约束和软偏好。

  • missing_slots：流程启动前还缺什么。
  • hard_constraints：必须满足，比如预算上限、不能修改某文件、必须使用某工具。
  • soft_preferences：尽量满足，比如更轻、更好看、更适合面试表达。

我觉得这一点非常关键：约束应该贯穿本轮对话，而不是在意图识别阶段用完就丢。很多 Agent 令人恼火，就是因为它识别到了用户约束，却在工具调用或最终回答里无视它。

评估指标

第二讲的评估部分可以直接变成面试回答模板：

  • Top1 Accuracy：第一候选是否命中标准答案。
  • Top-K Accuracy：标准答案是否出现在前 K 个候选里。
  • 分意图准确率：避免高频意图掩盖低频但重要意图。
  • 拒识准确率、误拒率、漏拒率。
  • 澄清触发准确率、澄清后收敛率。
  • 槽位准确率、槽位召回率、必填槽位完整率、槽位更新准确率。
  • 约束识别准确率。
  • 端到端任务成功率。

测试集要覆盖标准表达、口语化表达、槽位缺失、拒识、容易混淆样本。进阶测试还要覆盖跨轮补充、约束识别、意图切换和多意图输入。

03：提高准确率的五类问题与解法

第三讲的重点是：意图识别不准，不要只怪模型。很多时候是意图体系设计、上下文管理、候选召回、边界定义和仲裁机制出了问题。

为什么不准

课程总结了几个根因：

  • 意图太多：需求一来就加意图，候选集合越来越大，Prompt 放不下，模型也更容易混淆。
  • 边界重叠：比如推荐和比较并不总是正交，比较往往是为了做购买决策。
  • 用户表达不标准：口语、黑话、行业暗语无法直接映射到标准意图。
  • 一句话多目标：既要优化项目，又要生成面试追问。
  • 多轮时间线复杂：用户可能补充参数、修改需求、取消任务、切换任务、恢复任务。

解法一：层次意图

层次意图就是把意图组织成菜单或决策树：先识别一级领域，再识别二级任务，最后定位最小意图。它的优点是降低单次分类难度，结构清晰，准确率较高；缺点是可能需要多轮模型调用，性能较差。

适合场景：意图数量多、层级天然清晰、准确性比延迟更重要。

解法二：先检索候选意图

如果意图很多，不要把所有候选都塞进 Prompt。可以先用检索缩小候选集合，只把最相关的 N 个意图交给模型精排。

N 可以动态调整：上下文窗口空闲时多给一些，识别失败重试时扩大候选范围。也可以用轻量模型先粗筛，再用深度模型做最终判断。

这个思路本质上是“动态上下文”：不同阶段放进窗口里的东西不同，不要把所有信息一股脑塞进去。

解法三：动态 few-shot

few-shot 不是越多越好。固定 few-shot 适合描述必须遵守的规则，比如 unclear 和 unsupported 怎么处理；动态 few-shot 则应该根据当前输入检索最相关案例。

可以把历史 few-shot 存在普通数据库、搜索引擎或向量数据库里。每次拼 Prompt 前，检索最相关的正例和反例注入进去，减少无关示例对模型的干扰。

解法四：意图正交化

如果两个意图重叠，有两个处理办法：

  • 拆分新意图：把 A、B 和 A/B 重叠部分拆成三个互斥意图。
  • 合并意图，把差异下沉为参数：不要所有差异都建模成新意图，有些差异应该是槽位或参数值，再用代码判断。

这条很有工程味：能用确定性代码处理的不确定问题，就不要全丢给大模型。

真正多意图会带来性能、上下文、并发控制和依赖分析问题。更务实的策略是：每次先做一件事，完成后询问用户是否继续处理下一件。这样交互更自然，也更省成本。

解法六：向量匹配兜底

把典型的“用户输入 -> 意图”样本向量化，线上输入来了以后做相似度匹配。相似度足够高，就直接命中对应意图。

这适合两种场景：

  • 专属领域 Agent，用户输入模式有限。
  • 有大量业务黑话、内部表达、奇怪输入，需要长期沉淀兜底样本。

向量样本可以来自离线分析、用户反馈、人工排障和线上误判复盘。这个机制很适合面试，因为它体现了业务经验沉淀和反馈闭环。

解法七：不识别，后回滚

这是偏效率优化的策略：如果大部分多轮对话意图稳定，可以先复用上一轮意图，跳过识别；如果后续执行发现不对，再回滚并触发意图识别。

它适合用户很少切换任务的系统。面试里这个点比较特别，能体现你不是只会堆模型，而是会根据用户行为优化链路。

解法八：多识别器仲裁

可以引入多个识别器：规则、向量、轻量模型、深度模型。它们分别输出意图和置信度，再投票或加权仲裁。票数相同或分数接近时触发澄清。

这个方案理论上完整，但实践性价比未必高。适合拿来讲复杂系统设计，不适合所有小 Agent 都硬上。

解法九：微调

微调也能提升意图识别准确率，但它是双刃剑。面试官会追问数据准备、标注策略、评估方法、参数调优和线上回归。没准备好时，不如先讲向量兜底、动态 few-shot 和意图正交。

用 v0/v1/v2 讲方案演进

课程给的面试结构非常好用：

  • v0：只有一次大模型调用，没有输入规范化，没有效率优化，没有准确率统计，边缘输入处理差。
  • v1：分阶段优化。先引入轻量模型处理标准输入，再引入规则或向量兜底，最后加入动态 few-shot、输入规范化、拒识澄清、反馈沉淀。
  • v2：未来规划。可以考虑多意图、微调、离线分析、在线复盘、根据下一轮用户反馈评估上一轮识别效果。

这种表达的好处是有成长轨迹：你不是一上来就端出一个复杂架构，而是从问题出发，逐步演进。

对应链路是：

  1. 先做输入规范化，解决指代、省略、黑话、主观词。
  2. 规则和向量先跑，命中强规则或高相似样本就直接返回。
  3. 轻量模型处理标准输入。
  4. 深度模型处理复杂上下文、多轮切换、多意图。
  5. 低置信度进入澄清，高风险 unsupported 直接拒识。
  6. 输出 intent、slots、constraints、confidence 和 next_action。
  7. 线上误判回流，沉淀动态 few-shot 和向量兜底样本。

最终复盘

这 4 讲给我的最大提醒是：意图识别不是一个模型调用点，而是一套工程体系。它前面连接输入规范化，后面连接 Prompt / Spec、上下文、工具、Plan 和评估反馈。

面试里真正有区分度的回答，不是“我让大模型判断用户意图”，而是能说清楚：

  • 用户输入不规范怎么办。
  • 候选意图太多怎么办。
  • 意图边界重叠怎么办。
  • 参数缺失和约束怎么处理。
  • 识别失败时拒识还是澄清。
  • 多轮任务切换怎么识别。
  • 准确率怎么测，错例怎么回流。

如果只记一个判断标准，我会记这个：好的意图识别系统，不追求每次都猜，而是追求让后续执行走在正确轨道上。该确认时确认，该拒识时拒识，该回滚时回滚，这才是工程上的成熟。
