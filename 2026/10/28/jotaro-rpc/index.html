userService 是接口，实现在另一个进程里。JRpc 把这次方法调用收成一帧二进制，用 Netty 送过去，对端按接口名找到实现、过令牌桶、反射执行，再把 User 送回来。连接用完即关。

仓库在 jotaro-rpc，版本 1.0.6-SNAPSHOT。下面按动手的顺序写：报文、代理、协议、注册、发现、服务端执行。每段先讲这段代码在链路里干什么，再给出仓库里的实现。

1. 一次调用长什么样

远程调用要能在对端还原成一次 Java 方法调用，所以请求里带齐四样东西：哪个接口、哪个方法、参数值、参数类型。类型必须单独带，JSON 过网之后数字和对象的运行时类会对不上方法签名。

回来的包同样简单。code = 0 是成功，code = -1 是失败，原因写在 message。dataType 留给客户端把 JSON 变回原来的返回类型。

RespCodeEnum 里成功是 0，未知错误是 -1。

2. 动态代理把接口变成请求

业务代码拿不到实现类。getProxy 用 JDK 动态代理生成一个实现，方法调用全部进 invoke。这里把 Method 拆开，填进上一节的 RpcRequest，然后交给 NettyRpcClient。

代理只把 data 交回去。响应对象本身是 null，抛 IllegalStateException。限流、找不到服务、发送失败走的是 RpcResponse.fail，data 为空，调用方拿到 null。

3. 自己写一帧协议

TCP 是字节流，两条消息粘在一起时对端不知道从哪切开。JRpc 用两层长度。外层 4 字节由 Netty 的 LengthFieldPrepender 负责，解决粘包。内层是编码器自己写的业务头。

JotaroEncoder 只写内层。请求写 0，响应写 1，接着写序列化类型、包体长度和包体。当前 pipeline 塞进去的是 JsonSerializer，类型值是 1。

解码时外层 4 字节已经被 LengthFieldBasedFrameDecoder 剥掉，缓冲区从 msgType 开始。按类型找到序列化器，读出包体，还原成 RpcRequest 或 RpcResponse。

Type2SSerializerEnum 把帧头里的数字映射到类：0 是 ObjectSerializer，1 是 JsonSerializer，用 newInstance() 创建。两端现在都发送 JSON。对端把类型写成 0 时，这段解码会走 Java 原生序列化。

4. 挂上 Netty Pipeline

客户端和服务端的 pipeline 一样，最后一个 handler 不同。addLast 的顺序决定加工顺序：入站从头到尾，出站从尾到头。所以写出时先经过 JotaroEncoder，再由 LengthFieldPrepender 在最前面补 4 字节帧长。

LengthFieldBasedFrameDecoder 的五个参数：最大帧长、长度字段偏移、长度字段占 4 字节、长度调整值 0、解码后跳过 4 字节。跳过之后，JotaroDecoder 读到的第一个 short 就是消息类型。

5. JSON 过网后把类型捞回来

JsonSerializer 用 Fastjson2。反序列化打开 SupportClassForName，请求里的 Class[] 和响应里的 dataType 才能变回类。

自定义对象从 JSON 回来经常是 JSONObject，直接拿去 Method.invoke 会对不上参数类型。所以每个参数先做一次兼容检查，对不上就按声明类型再转一次。

返回值同样处理。服务端成功时把 method.getReturnType() 放进 dataType，客户端解码时如果 data 的类对不上，再 JSON.to(dataType, data)。User 能变回 User，靠的就是这个字段。

Java 原生序列化在 ObjectSerializer 里，用 ObjectOutputStream 写、ObjectInputStream 读，类型留在字节流里。RpcRequest、RpcResponse、User 都实现了 Serializable。当前 pipeline 发送的是 JSON。

6. 实现类挂进 ZooKeeper

服务端做两件事：本地留一张「接口名 → 实现」的表，供反射查找；ZooKeeper 上留一个临时节点，供客户端发现。

一个实现类有几个接口，就注册几条服务。

ZooKeeper 分两级。服务路径是永久节点，进程退出后还在，避免服务名本身消失。实例是临时节点，会话断了 ZooKeeper 会把它删掉。地址写在路径最后一段，节点 data 是空的。

本地 Map 的写入在 ZKWatcher。它监听命名空间根，本意是节点创建就放进缓存。路径解析用的是节点 data：

注册临时节点时没有写入 data，切出来的段数到不了「服务名 + 地址」。缓存因此一直是空的，serviceDiscovery 每次走到 getChildren。真正选出地址的是下面这段。

默认均衡是轮询。choose 从 -1 开始，第一次取到下标 0。

随机均衡是 new Random().nextInt(addressList.size())。换实现只改 ZKServiceCenter 构造里的 this.loadBalancer。

一致性哈希给每个真实地址挂 10 个虚拟节点，名字是 地址#序号，放进 TreeMap。查找时对一个随机整数做哈希，顺着环取下一个节点，到尾部就回到第一个，再截掉 # 后面的序号。

哈希输入是随机数，同一次调用的参数不会把流量粘在固定节点上。10 个虚拟节点把随机点摊到各真实地址。构造方法必须传入 Function<String, Integer>，它会覆盖类上那份 FNV-1a 初值。

8. 服务端先限流，再反射

包到了 NettyRpcServerHandler。先按接口名查本地表，再按方法名和参数类型找到 Method，取到令牌才 invoke。写完响应立刻关掉连接，关闭放在写出完成之后，避免对端还没读到字节连接已经断了。

令牌桶按 接口名#方法名 懒创建，参数是 (补充间隔毫秒, 容量)，也就是 100 毫秒、容量 10。一开始桶是满的，连续 10 次直接减库存放行。

库存到 0 之后，不满 100 毫秒就拒绝。满 1 个间隔，本次放行，库存仍是 0。满 2 个及以上间隔，把「间隔数 − 1」补进桶里并封顶 10，本次另外放行。getToken 没有加锁，同一方法上的并发请求会一起改 curCapacity。

9. 从这条连接上拿回结果

客户端的 Bootstrap 和 EventLoopGroup 是静态的，channel 每次新建。连上、写出、等到连接关闭，再从 channel 的 attribute 里取响应。一次调用一条连接。

服务端把响应写进这条连接之后，客户端 handler 只做两件事：塞进同一个 attribute，然后关闭 channel。sendRequest 堵在 closeFuture 上，关完就能 attr.get()。

重试单独放在 GuavaRetryHandler。异常就重试；结果是 null，或者 code 和成功枚举对不上，也重试。固定等 2 秒，一共调用 3 次。

notEqual 比较的是枚举 RespCodeEnum.SUCCESS 和响应里的 Integer code，两者对不上，非空响应也会进入重试。默认代理调用的是 sendRequest，这条重试要自己接上 RpcClient 才会生效。
